Sección 01
Portada y resumen ejecutivo

Contexto del reto

Heredamos un servicio que lleva diez años en producción. No existe código fuente ni documentación, y las dos personas que lo desarrollaron ya no están disponibles. Sabemos que recibe mensajes y devuelve respuestas. Si se apaga, la empresa deja de funcionar.

Objetivo principal

Comprender el comportamiento observable del servicio y construir un reemplazo que responda exactamente igual que el original, incluidos sus errores y casos límite.

Problema de negocio

La dependencia de un sistema opaco representa un riesgo crítico. Cualquier fallo o necesidad de migración es imposible de planificar sin conocer el contrato real del servicio.

Enfoque de solución

  1. Investigación controlada: enviar entradas al servicio original, registrar salidas exactas.
  2. Análisis sistemático: deducir reglas a partir de observaciones, no suposiciones.
  3. Especificación: documentar cada comportamiento con evidencia y nivel de confianza.
  4. Implementación independiente: construir reemplazo sin llamar al original.
  5. Validación diferencial: comparar reemplazo vs. original secuencia por secuencia.

Restricciones principales

  • No utilizar herramientas que hagan la ingeniería inversa automáticamente.
  • Scripts y fuzzers propios sí están permitidos.
  • El reemplazo no puede invocar al servicio original ni a otro reemplazo.
  • La solución debe entregarse desplegada y accesible desde internet.

Entregables esperados

  • Reemplazo del servicio desplegado.
  • Especificación del comportamiento observado.
  • Registro de experimentos (experimentos.jsonl).

Sección 05
Diseño del sistema

Decisiones arquitectónicas iniciales

ADR-01 · Separación entre investigación y ejecución

El entorno de fuzzing y el reemplazo desplegado deben ser código completamente separado. Esto garantiza que el reemplazo nunca llame al original por accidente o diseño.

ADR-02 · Modularidad para refinamiento de reglas

Cada comando (PING, ALTA, TRANSFER, etc.) se implementa como módulo independiente. Si un experimento refuta nuestra comprensión de ALTA, solo ese módulo se modifica sin afectar el resto.

ADR-03 · Aislamiento del acceso al servicio original

El reemplazo se prueba en un entorno sin conectividad de red al original. Si falla, hay una dependencia oculta que debe eliminarse.

ADR-04 · Pruebas diferenciales

La validación principal no es "¿funciona?" sino "¿responde exactamente igual que el original?". Se compara byte a byte para secuencias de referencia.

ADR-05 · Trazabilidad de decisiones

Cada regla en la especificación vincula al menos un experimento (id de experimentos.jsonl). Sin evidencia, la regla se marca como Propuesto o Supuesto.

ADR-06 · Distinguir confirmado de hipótesis

Los comportamientos se clasifican en confirmado (repetible), probable (observado una vez o inferido) y supuesto (no probado, comportamiento por defecto).

Responsabilidades de cada componente

  • Router: expone endpoints del contrato (/health, /__reset, /msg). Delega parseo y ejecución.
  • Parser: divide el mensaje por separador, normaliza case, valida aridad por comando.
  • Validador: verifica formato del campo de control (checksum/dígito verificador). Pendiente de descubrir.
  • Motor: ejecuta la lógica de negocio contra el estado actual del token.
  • Estado: diccionario en memoria (dict[token, TokenState]). Persiste solo durante la vida del proceso.
  • Gestor de errores: catalogo de códigos E201–E507 con status y mensaje exacto.

Flujo de procesamiento

Request → Router → Parser → Validador → Motor → Estado → Respuesta
                      ↓           ↓
               Error parse   Error validación
                      ↓           ↓
               Respuesta exacta de error

Manejo de errores

El orden de evaluación de errores es crítico y aún Pendiente de validar. Propuesta:

  1. Comando desconocido → E301
  2. Aridad inválida → E302
  3. Control mal formado (no numérico) → E201
  4. Control inválido (numérico pero valor erróneo) → E202
  5. Cuenta inexistente → E401
  6. Límite excedido / saldo insuficiente → E506 / E507

Consideraciones de seguridad

  • Autenticación por Authorization: Bearer <token>. El reemplazo debe replicar este comportamiento sin inventar tokens.
  • Rate limit: 10 req/s, 8000/día. El reemplazo no aplica rate limit propio (la evaluación no lo menciona), pero debe ser capaz de soportar la carga.
  • El reemplazo no realiza requests salientes: verificar con inspección de tráfico.

Sección 07
Estrategia de ingeniería inversa

Procedimiento incremental de siete fases. No se generaliza de una sola observación.

Fase 1. Reconocimiento

  • Revisar material oficial (README, ejemplos, reglas de evaluación).
  • Identificar cómo ejecutar el servicio original: URL, autenticación, endpoints.
  • Determinar protocolo y mecanismo de comunicación.
  • Establecer entorno reproducible: scripts, token, reset entre secuencias.

Fase 2. Casos de referencia

  • Reproducir los 20 ejemplos proporcionados exactamente.
  • Registrar respuestas completas: status, headers, body, latencia.
  • Registrar errores, timeouts, cierres de conexión si aplica.
  • Repetir experimentos para identificar determinismo o variabilidad.

Fase 3. Exploración sistemática

  • Variación un parámetro a la vez.
  • Probar: valores vacíos, límites, tipos inesperados, entradas malformadas.
  • Desarrollar scripts y fuzzers propios.
  • Investigar casos límite sin depender de herramientas automáticas.

Fase 4. Formulación de hipótesis

  • Documentar patrones observados.
  • Diseñar experimentos que distingan entre hipótesis competidoras.
  • Ejemplo: ¿el control es suma de dígitos, suma ponderada de ASCII, o checksum propietario?

Fase 5. Especificación

  • Traducir hallazgos en reglas verificables.
  • Identificar ambigüedades explícitamente.
  • Relacionar cada regla con evidencia de experimentos.jsonl.

Fase 6. Validación

  • Comparar reemplazo con referencias registradas.
  • Corregir divergencias byte a byte.
  • Ejecutar pruebas de regresión tras cada cambio.

Fase 7. Preparación para entrega

  • Comprobar independencia del original (sin requests salientes).
  • Verificar despliegue accesible.
  • Confirmar formatos de entregables contra README oficial.

Flujo de fases

flowchart LR A["1. Reconocimiento"] --> B["2. Casos de referencia"] B --> C["3. Exploración sistemática"] C --> D["4. Formulación de hipótesis"] D --> E["5. Especificación"] E --> F["6. Validación"] F --> G["7. Preparación entrega"] F -->|divergencia| C D -->|hipótesis inválida| C

Reglas de oro

  1. Un cambio por experimento. Si mutás dos cosas y falla, no sabés cuál causó el cambio.
  2. Reset antes de cada secuencia. El estado es enemigo de la reproducibilidad.
  3. Loguear todo. Un experimento no logueado es un experimento no hecho.
  4. No generalizar de N=1. Repetí al menos 3 veces.
  5. Ruido vs señal. Diferencias de timestamps = ruido. Diferencias de saldo = señal.

  • Formato de entrada: protocolo, método, ruta, headers, cuerpo.

Sección 10
Estrategia de pruebas

Categorías de pruebas

1. Pruebas de referencia

Reproducir exactamente los 20 ejemplos del material oficial. Secuencia completa tras POST /__reset. Comparar status y body.

2. Pruebas de equivalencia diferencial

Dada una secuencia de requests: ejecutar contra original → capturar. Ejecutar contra reemplazo → capturar. Comparar diff.

3. Pruebas de regresión

Conjunto de secuencias que pasaron en versiones anteriores del reemplazo. Se ejecutan en CI o antes de cada commit.

4. Pruebas de casos límite

Monto cero, negativo, muy grande. Nombres vacíos, con espacios, unicode. Transferencia entre misma cuenta. Anulación de operación ya anulada.

5. Pruebas de errores

Cada código de error (E201–E507) debe tener al menos un test que lo dispare. Verificar status exacto y body exacto.

6. Pruebas de entradas malformadas

JSON sin campo m, campo m vacío, caracteres no-ASCII en comando, separadores faltantes o extra.

7. Pruebas de independencia

Ejecutar reemplazo sin conectividad de red. Verificar que no hace requests salientes (inspección de tráfico, mock de socket).

8. Pruebas de despliegue

GET /health responde 200. POST /__reset limpia estado. Reemplazo responde en < 5 segundos por request.

Política de comparación

Tipo de datoPolítica
Ambos JSONClaves en cualquier orden, arrays en orden, strings/numbers idénticos
Alguno no es JSONComparación carácter por carácter exacta
Status HTTPDebe ser idéntico
HeadersNo se comparan en evaluación oficial

Cobertura conceptual

No presentamos porcentajes ficticios. La cobertura se mide en:

  • Comandos distintos testeados / comandos conocidos.
  • Códigos de error disparados / códigos conocidos.
  • Secuencias de estado testeadas / comportamientos de estado identificados.

Inicialmente: 0% confirmada. La cobertura crece con cada experimento.

Sección 11
Despliegue y ejecución

🚀

Desplegado. El reemplazo está activo en https://caja-negra-replacement.vercel.app. Todos los 20 ejemplos del repositorio pasan contra la instancia remota.

Requisitos

  • Python 3.12+
  • FastAPI + Mangum (para serverless) + uvicorn (para local)
  • Sin dependencias de red al servicio original

Instalación

pip install -r requirements.txt

Configuración

VariableValorDescripción
PORT8000Puerto de escucha (local)
AuthorizationBearer <token>Header obligatorio en /msg, /__reset

Ejecución local

uvicorn src.main:app --host 0.0.0.0 --port 8000

Verificación de salud

  • GET /health responde 200 OK (confirmado).
  • POST /__reset limpia el estado por token (confirmado).
  • POST /msg con JSON {"m": "COMANDO;...;control"} (20/20 ejemplos reproducidos).

Independencia del servicio original

🔒

Crítico. El reemplazo debe poder iniciarse y funcionar en una máquina sin acceso a internet. Verificar con iptables -A OUTPUT -d <ip-original> -j DROP o equivalente.

Sección 12
Riesgos y mitigaciones

Riesgo Impacto Mitigación Estado
Cobertura insuficiente de entradas Alto Fuzzing sistemático, variar un parámetro a la vez, usar múltiples tokens en paralelo Mitigación propuesta
Falsas conclusiones de pocos experimentos Alto Regla: no generalizar de N=1. Repetir 3 veces. Marcar confianza como probable/supuesto Mitigación propuesta
Comportamientos dependientes del estado Alto Reset antes de cada secuencia. Secuencias controladas de 2–12 requests. Comparar saldos Mitigación propuesta
Respuestas no deterministas Medio Repetir secuencias idénticas. Si difieren, documentar como variable y buscar causas Mitigación propuesta
Errores no reproducibles consistentemente Medio Loguear condiciones exactas. Distinguir errores de infraestructura vs. errores del servicio Mitigación propuesta
Diferencias sutiles de formato Medio Comparación byte a byte, no solo lógica. Verificar espacios trailing, orden de claves JSON Mitigación propuesta
Tiempo limitado para exploración Alto Priorizar fuzzing de alta información (control, aridad, límites). Automatizar regresión Mitigación propuesta
Despliegue incompatible con entorno de evaluación Alto Deploy temprano en plataforma similar (Railway). Probar entrypoint en /evento antes del deadline Pendiente
Servicio original cambia durante el día Alto Monitorear con health_check periódico. Versionar capturas. Ajustar reemplazo si hay diffs Mitigación propuesta
